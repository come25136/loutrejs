# コーディングと設計レビューで受けた指摘

この会話でユーザーが繰り返し重視した判断基準を、次の作業へ引き継ぐ。共通の言語・記述責務・コミット・型assertionの規約は[AGENTS.md](../AGENTS.md)を正本とし、ここでは指摘の背景とレビューの観点を残す。現在のAPIと個別の設計判断は各ADRを参照する。

## 破壊的変更を許可された場合の進め方

- 開発中の社内向けPJでは、後方互換やデータ移行を目的とする分岐・alias・暫定構造を残さず、理想的でKISSな構成へ書き換える。
- 資料を先に更新して矛盾を解消し、保証したい振る舞いのテストを書き、最小実装し、最後に不要コードと資料の不整合を確認する。
- 修正範囲の小ささより、責務の所有者・依存方向・状態の寿命が自然であることを優先する。必要なら呼び出し元とRuntimeも一緒に変更する。
- ファイル構成も大きく変更してよい。構造の再編では既存テストの内容と期待値を維持し、保証が不足していることに気づいたらテストを追加する。

## 機能追加よりアーキテクチャの一貫性を優先する

ユーザーが特に気にしているのは、MCPが動くことだけでなく、追加によってLoutre全体のアーキテクチャが汚くならないこと。同じ責務を持つ既存機能との比較を省略しない。

- 新しい概念を追加する前に、その機能だけに必要なのか、Coreへ置く必要があるのか、既存の仕組みで表現できないのかを確認する。
- MCPとGraphQLの違いをprotocol名や「transport配下」「独立Execution」といった呼称だけで説明しない。生成・依存解決・実行・終了の実際の差を示す。
- 共通化する案も比較する。共通の責務は同じ仕組みに載せ、非対称を残す場合は具体的な要件と理由を示す。
- 公開API、canonical Application Model、実際のRuntimeが同じ所有権を表すことを確認する。統一したと説明する前にExtension内部まで確認する。
- handlerなどから導出できる依存情報を、各呼び出し元へ手作業で転記させない。収集・集約はその情報を所有する責務へまとめ、Runtimeには実行に必要な契約だけを渡す。

今回の採用判断は[Execution Extension契約](../../docs/adr/loutre_execution_extension_contract_architecture.md)に記録する。`ExecutionGroup`は宣言の合成、delegateは登録済みExecutionへの接続という異なる責務を持つため、存在する理由を個別に説明する。

## 状態とDIの共有範囲を具体化する

「共有する」「リクエストごと」といった説明だけでは不足する。比較表とライフサイクル図では、各状態について次を明示する。

| 観点   | 確認すること                                                                           |
| ------ | -------------------------------------------------------------------------------------- |
| 所有者 | Application、endpoint、transport、接続、operationのどこが持つか                        |
| 生成   | Definitionの宣言時、依存収集時、起動時、呼び出し時のどこで作るか                       |
| 共有   | HTTPとWebSocket、同じendpointの複数呼び出し、別endpoint、別Applicationの間で共有するか |
| DI     | どのModuleのvisibilityで依存を解決し、注入後のinstanceをどこが保持するか               |
| 終了   | 誰が中断を通知し、誰の完了を待ち、いつ参照とresourceを解放するか                       |

- 一つのHTTP listenerへ複数endpointを配備できる。listenerが一つであることを、protocol runtimeもApplication内で一つにする根拠にしない。
- factoryで取得して保持するtransient Providerと、呼び出しごとに生成するContextを混同しない。transientという名前だけで毎回作られると説明しない。
- stateやContextで渡せる呼び出し情報のために、静的なExecutionや別のDI resolverを増やさない。Model上の宣言と実行時のoperationを区別する。
- signalの中断と処理の完了を区別する。SDKが先に応答しても、継続中のhandlerが使うRuntimeやProviderを先に破棄しない。

共有範囲の正本は[GraphQL設計](../../docs/adr/loutre_graphql_transport_architecture.md#状態の寿命と共有範囲)と[MCP設計](../../docs/adr/loutre_mcp_server_architecture.md#状態の寿命)とする。

## 分岐と型の整理を後回しにしない

- `factory`と`delegate`の存在判定をcompileやRuntimeの各段階で繰り返す構造は、既存APIへの継ぎ足しとして指摘された。破壊的変更を前提に、宣言の入口から共通の契約へ揃える。
- union自体を問題視しない。責務境界の要求・結果そのものの種類は明示的な`kind`を持つ閉じたunionにし、受け手が`ts-pattern`の`match(...).exhaustive()`で網羅する方針が採用された。状態には`status`を使う。
- `kind`はドメイン属性より一段上の種類を表す。GraphQL Contextの`transport`を`kind`へ改名した変更は広げすぎとして指摘された。意味のある属性名を維持し、網羅性の保証と機械的な命名統一を混同しない。
- 種類と必要な値の対応をoptional fieldや任意callbackへ隠さない。同じ判定を複数段階へ持ち回らず、境界で一度処理して共通の内部表現へ変換する。詳細は[責務境界の契約ADR](../../docs/adr/loutre_typed_boundary_contracts.md)を参照する。
- 型の不整合をassertionで隠さない。入力検証、型付きの値の構築、型宣言の修正で解消し、middleware stateとContextの推論を維持する。禁止するassertionの詳細は[AGENTS.md](../AGENTS.md#型assertion)に従う。

## 設計の説明と検証

- 構成の説明にはMermaidを使い、必要に応じて起動・実行・中断・終了まで展開する。比較では同じ観点の表を作り、共有範囲を曖昧にしない。
- ADRは最終的に目指す構成と採用理由へ書き直す。旧案と新案の混在を残さない。
- exampleとsmoke testを用意し、実際に利用できることを確認する。型テストの成功だけで、宣言出力や配布パッケージも利用できるとは判断しない。
- 型とテストが通ることに加え、不要な概念・重複・暗黙の共有状態が残っていないかをレビューする。
- 境界や終了処理の不具合を見つけたら、同じ責務を使う経路をまとめて調べ、処理完了とresource解放の順序を回帰テストで保証する。局所修正の完了を全体レビューの完了として報告しない。
- 実装済み、検討のみ、未対応を明確に分けて報告する。`ts-pattern`の適用など、確認していないことを実施済みとして扱わない。
