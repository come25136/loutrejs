# ApplicationのLoggerと資源終了の所有権

- 状態: IMPLEMENTED
- 日付: 2026-11-03 JST
- 対象: #174

## 背景

Applicationの外でLoggerを生成すると、backendが必要とするEnvironmentやProviderの依存がModelに現れず、Runtimeと注入先の構築・終了責務も分かれる。Loggerを通常のapplication scope Providerとして直接注入すると、consumerごとのsourceを一つのinstanceへ保持できない。

## 判断

ApplicationのLoggerは予約tokenの`LoggerToken`に通常Providerとして登録する。公開例は`provide(LoggerToken).useClass(LoggerService)`とし、取得は`inject(LoggerToken)`へ分ける。Logger専用の設定factoryや`inject()`への登録用overloadは設けない。

class providerの省略形はそのクラス自身への登録であり、別の予約tokenへの対応付けは`provide(...).useClass(...)`で明示する。選択用の独自tokenと`application.logger`を両方要求すると、通常Provider登録とは別の構成経路ができるため採用しない。予約tokenの宣言をApplication直下Moduleからexportし、Application全体へ適用する。backend内部には通常のModule visibilityを維持する。

Loggerはapplication scopeのrootとして構築し、`inject(LoggerToken)`ではconsumerのsourceを付けたchildを返す。`app.get(LoggerToken)`はrootを返し、sourceは`Application`とする。実体とbackendは共有し、sourceを利用側へ手書きさせない。既存の`Logger`クラスも同じ予約tokenの別名として維持する。

Loggerとbackendの依存は通常のProvider nodeとedgeでModelへ含める。投影専用のframework nodeや別Containerは設けず、rootから予約tokenへ戻る循環は構築前に診断する。未指定時もclass Providerを補い、同じDefinitionから起動したApplicationが実体を共有しないようにする。`useValue`で利用者が明示的に共有する場合には通常Providerと同じ規則を適用する。

portableなLoggerとconsole backendはCoreに置く。Modelが既定Providerを宣言するためにRuntime実装へ逆依存しないためであり、従来のruntime exportも維持する。

予約tokenとLogger実体の識別にはbundle間で共通のsymbolを使う。クラス参照や`instanceof`だけで判定すると、bundleに含まれたProviderをHostのContainerで構築した場合に別クラスとして拒否してしまう。予約tokenの印はクラス自身が持つ場合だけ認め、派生クラスを通常Providerとして登録できるようにする。

## 構築とlifecycle

Containerが実際に生成したapplication scopeのinstanceをKernelが記録し、依存から順に`onModuleInit`を実行する。rootとその依存はruntime inputのbind後、ほかのProviderより先に準備する。conditional providerの未選択候補を初期化順の計算だけのために生成しない。Moduleのhookは従来どおりModuleの初期化時に実行する。

初期化失敗時の回収対象をModuleの走査完了から推測しない。失敗したconstructorやfactoryが先に解決した依存も、生成済みinstanceの記録から回収する。同じ実体を複数tokenで公開してもinstanceのlifecycleは一度だけ実行する。

shutdownの既存フェーズは維持し、その後に汎用の`onApplicationDispose`を追加する。全Moduleのdispose hookを実行した後、実体を生成の逆順にdisposeする。shutdown中も必要なbackendや接続はこの最終フェーズでflush・closeする。初期化rollbackでも`onModuleDestroy`の後にdisposeし、一つの資源の失敗で残りの回収を中断しない。ProviderのDisposable protocolは自動実行しない。

Loggerだけの終了registryを設けたり、backendを`onModuleDestroy`で先に閉じたりすると、終了中に出すログの寿命を保証できない。資源の最終解放を共通フェーズに置き、Loggerからbackendの終了処理を直接呼ぶ方式も採用しない。

## 準備前と終了後の診断

rootの準備前に失敗した場合は元の例外を呼び出し元へ返す。Kernelは未完成のLoggerを再解決せず、ログのbufferや別Loggerを使った依存解決の再試行も行わない。

rootはdispose時にchildと共有する出力状態を終了済みにする。以後の出力はconsoleへ送り、終了済みbackendへ再度書き込まない。Runtimeが全資源の解放後に受け取る終了失敗もこの経路で診断する。drain待ちで資源を保持している間は同じbackendを使用する。console出力はApplicationのbackend共有の対象外となる障害境界であり、通常のログ設定として別のbackendを並走させるものではない。
